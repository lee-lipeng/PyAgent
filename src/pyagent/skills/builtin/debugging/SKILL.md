# 系统化调试技能

当用户报告程序问题时，遵循系统化调试方法论。

## 核心调试循环

1. **可靠复现**：获取一个每次都能触发 bug 的命令。
   如果是偶发问题，先固定非确定性因素（随机种子、执行顺序、时序）。
2. **缩小范围**：用更少的数据、更小的模型、单进程、单线程。
   2 秒能复现胜过 2 分钟。
3. **定位根因**：确认你在编辑实际运行的代码（而非缓存/旧版本），
   然后二分搜索：哪个 commit、哪个文件、哪个函数、哪行代码。
4. **获取信号**：将模糊失败转为精确信息——
   traceback、stack dump、边界值打印、变量检查。
5. **改一件事、验证**：在快速复现上修复，确认，再扩展到完整场景。

## 按症状选工具

| 症状 | 工具/方法 |
|------|----------|
| 卡住/无输出 | `py-spy dump`、`strace -p <pid>`、`gdb -p <pid>` |
| 段错误/崩溃 | core 文件 + `gdb`（`bt`、`bt full`、`thread apply all bt`） |
| 内存溢出(OOM) | 区分 forward/backward 阶段；检查内存碎片化；内存分析器 |
| 神秘 CUDA 错误 | `CUDA_LAUNCH_BLOCKING=1` 或在 CPU 上运行 |
| NaN/Inf | 检查每个 tensor 的 min/max/NaN；下溢/上溢检测 |
| "修改没生效" | 确认运行的是编辑后的代码（`print` 验证）；检查 `pip install -e .` |
| 回归出现 | `git bisect run` 二分定位引入问题的 commit |
| 脚本静默失败 | `set -euo pipefail`、`set -x` |

## 调试原则

- **先观察再猜测**：不要在没有信号的情况下猜测原因。
- **确认运行的是你编辑的代码**：修改前先验证代码路径。
- **一次只改一个变量**：同时改多处会让定位失效。
- **快速复现优先**：能 2 秒复现就不要用 2 分钟的完整流程。
- **保留复现命令**：调试结束后保留触发命令，用于回归测试。

## 常见陷阱

- **缓存/旧版本**：修改后没重新安装/编译，运行的是旧代码。
- **环境差异**：本地能跑但 CI 失败，检查依赖版本和环境变量。
- **并发竞态**：偶发问题多为竞态，固定执行顺序后复现。
- **静默失败**：脚本没有 `set -e`，错误被吞掉，看起来"正常"运行。
