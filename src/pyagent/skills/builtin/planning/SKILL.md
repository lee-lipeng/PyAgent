# 任务规划技能

当用户要求规划复杂任务时，遵循结构化规划流程。

## 何时使用

- 任务涉及多个文件或模块的修改。
- 需求模糊，需要先拆解再执行。
- 用户问"怎么做 X"或"如何实现 X"。
- 大型功能开发或架构变更。

## 规划流程

### 1. 理解需求

- **明确目标**：用户最终想要什么？成功的标准是什么？
- **识别约束**：有哪些技术限制、时间限制、兼容性要求？
- **确认范围**：哪些在范围内，哪些明确排除？

不确定时主动询问，不要基于猜测制定方案。

### 2. 调研现状

- 用 `list_dir` 了解项目结构。
- 用 `grep` 和 `find_files` 搜索相关代码。
- 用 `read_file` 阅读关键文件，理解现有实现。
- 识别可复用的代码和模式。

### 3. 拆解步骤

将任务拆解为可独立验证的子步骤：

```
## 实施步骤

### 步骤 1：<名称>
- 目标：这一步要完成什么
- 涉及文件：<文件列表>
- 验证方式：如何确认这一步完成

### 步骤 2：<名称>
- 目标：...
- 依赖：步骤 1
- 涉及文件：...
- 验证方式：...
```

**拆解原则**：
- 每步可独立完成和验证。
- 步骤之间有明确的依赖关系。
- 先做有风险的部分（不确定的技术方案先验证）。
- 每步控制在 1-2 小时工作量。

### 4. 评估风险

```
## 风险与对策

| 风险 | 可能性 | 影响 | 对策 |
|------|--------|------|------|
| API 不兼容 | 中 | 高 | 先写 spike 验证 |
| 性能下降 | 低 | 中 | 添加基准测试 |
| 破坏现有功能 | 中 | 高 | 确保测试覆盖 |
```

### 5. 制定验证标准

```
## 验证标准

- [ ] 功能标准：<具体的功能验收条件>
- [ ] 测试标准：<测试覆盖要求>
- [ ] 性能标准：<性能指标，如有>
- [ ] 兼容标准：<兼容性要求，如有>
```

## 规划原则

- **先调研再规划**：不要在不了解代码库的情况下制定方案。
- **小步可验证**：每步小到可以独立验证，降低返工成本。
- **先验证风险**：不确定的技术方案先做 spike（原型验证）。
- **保留备选方案**：主方案之外列出 1-2 个备选，说明取舍。
- **方案要具体**：给出文件路径、函数名、修改方向，不要停留在"优化架构"。

## 输出格式

```markdown
# <任务名> 实施方案

## 目标
<一句话说明目标>

## 现状分析
<代码库现状、可复用部分、约束条件>

## 实施步骤
### 步骤 1：...
### 步骤 2：...

## 风险与对策
<风险表格>

## 验证标准
<检查清单>
```
